**진짜 문제 정의(고정 전제):**

> 4×4 격자에 1~16을 각각 한 번 배치한 상태가, **행·열·대각선(총 10줄) 합 규칙을 모두 만족하는지** 일관되게 **판별**하고, 그 **판별 기준을 반복 가능하게 고정**하는 것.

**1차 범위(기본 가정 — 문서에서 명시적으로 확정·기록):**

- **판정기(validator)만** 1차 대상. 생성·UI·해 열거·동치 분류는 **비목표**.
- 격자 크기 **4×4 고정**. n×n는 「향후」로만 한 줄 언급 가능.

**문제 정의 보고서의 미결정 4항목**은 TDD 설계 문서에서 **반드시 결정안을 제시**하고, 각 결정에 **테스트에 미치는 영향**을 연결하라:

1. 미완성 격자 — 별도 상태 vs 단일 「비유효」
2. 출력 수준 — 유효/무효만 vs 위반 설명(줄·중복 값)
3. 이해관계자·시나리오 — 학습자 입력 vs 데모 고정 격자
4. 1차 범위 — 판정기만 고정(기본) vs 생성 포함 여부 명시

결정 시 **한 가지 권장안(Default)** 과 **대안(Alternative)** 을 표로 제시하고, 권장안으로 설계를 진행하라. 사용자 확인이 없어도 문서는 완결되어야 한다.

# 작성 방식

- **한 번에 완성된 최종 문서**를 출력하라. STEP별로 사용자에게 질문하며 멈추지 마라.
- 문제 정의의 Invariant **I-1 ~ I-12**를 빠짐없이 추적 표로 매핑하라.
- 테스트는 **Red → Green → Refactor** 순서로 **구현 착수 순서**까지 제안하라.
- 테스트 케이스는 **이름(영어 snake_case 또는 describe/it 스타일)** + **Given/When/Then** + **기대 결과** 형식.
- **의사코드·인터페이스 시그니처**는 「행위 계약」 수준만 허용. 특정 언어·프레임워크(Jest, pytest 등)는 **부록에서 1종만 예시**로 언급 가능하나, 본문은 언어 중립.
- 표·mermaid 다이어그램을 적극 사용하라. 한 줄 요약 표를 각 대절마다 둬라.
